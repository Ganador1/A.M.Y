## 2. Extended Data Model

<a id="21-objetivos"></a>
### 2.1 Objectives
- Represent hypotheses as living versioned entities with lineage, evidence, and multi-domain state.
- Guarantee reproducibility and auditability through manifests and hashes.
- Prepare the foundation for semantic graph and RAG.

<a id="22-esquema-propuesto-hypotheses-sql--alembic"></a>
### 2.2 Proposed Schema `hypotheses` (SQL / Alembic)
New fields (add to existing table):
- `domains_involved` (JSON TEXT) → Prioritized ordered list.
- `cross_validation_matrix` (JSON TEXT) → NxN matrix with cells `{compatibility: float, rationale: str, last_updated}`.
- `tool_artifacts` (JSON TEXT) → List `[{id, type, uri, hash, metadata}]`.
- `validation_history` (JSON TEXT) → Append-only events `{ts, actor, phase, result, metrics}`.
- `safety_assessment` (JSON TEXT) → `{risk_score, categories: [...], decisions: [...], gates_passed: bool}`.
- `publication_package_id` (TEXT NULLABLE)
- `lineage` (JSON TEXT) → `{parent_ids: [], children_ids: [], derivation: [{from, method, params_hash}]}`.
- `metrics_snapshot` (JSON TEXT) → Last computed object `{rigor, reproducibility, novelty, risk, consensus}`.
- `schema_version` (TEXT) → e.g. `hypothesis.v1`.

Additional indexes:
- `CREATE INDEX idx_hypothesis_domains_gin ON hypotheses USING GIN (domains_involved jsonb_path_ops)` (in future Postgres). For SQLite: auxiliary virtual FTS index.
- Index by `publication_package_id` and `schema_version`.

<a id="23-tabla-artifacts"></a>
### 2.3 Table `artifacts`
```
artifacts(
  id TEXT PRIMARY KEY,
  hypothesis_id TEXT NULL,
  type TEXT,            -- model|dataset|figure|structure|report
  uri TEXT,              -- ruta local o remoto
  hash TEXT,             -- BLAKE3
  metadata JSON TEXT,    -- dims, formato, tool origen
  created_at TIMESTAMP,
  reproducibility_tag TEXT -- semilla + env hash
)
```
Lightweight relationship: `hypotheses.tool_artifacts` maintains redundancy (denormalized cache) for fast reads.

  ref_id TEXT,           -- id en tabla origen

  properties JSON TEXT,
  embedding BLOB NULL,   -- vector opcional (FAISS/SQLite vss future)

```

knowledge_edges(

<a id="28-lineage-y-versionado"></a>
### 2.8 Lineage and Versioning
Copy-on-write pattern: when refining a hypothesis:
1. Clone record → new `id` preserving `parent_ids`.
2. Record lineage event `derivation`.
3. Propagate immutable artifacts (reference) and mark mutable ones.

<a id="29-estrategia-de-migración"></a>
### 2.9 Migration Strategy
1. New Alembic migration: add NULL columns + controlled default.
2. Incremental backfill: script that initializes empty fields (`[]`, `{}`) where `NULL`.
3. Validation: job that runs `pydantic_model.validate()` on each row and reports.

- Optional compression (zstd) for large matrices (>128KB) before persisting.

## 3. Detailed Layered Architecture

<a id="31-visión-general"></a>
### 3.1 Overview
Layers decoupled through internal events (`EventBus`) and Pydantic contracts. Avoid cyclic dependencies using inversion of control (interfaces + dynamic adapter registry).

```
[API Layer] -> [Hypothesis Core / State Machine] -> [Domain Agents] -> [Tool Adapters]
                                       |                |
                                       v                v
                         [Workflow Orchestrator]   [Resource Scheduler]
                                       |
                     [Validation & Peer Review Layer]
                                       |
                        [Knowledge & RAG Layer]
                                       |
                  [Persistence & Provenance Services]
                                       |
                 [Publication & Reporting Pipeline]
                                       |
                   [Monitoring / Ethics / Compliance]
```

<a id="32-componentes-clave"></a>
### 3.2 Key Components
| Layer | Component | Responsibility | Initial Tech Stack |
|------|------------|-----------------|--------------------|
| API | FastAPI Routers | CRUD, triggers, SSE streaming | FastAPI, Uvicorn |
| Hypothesis Core | State Manager | Cycle (create→expand→validate→refine) | State machine (transitions) |
| Domain Agents | Protein, Materials, Genomics, NLP | Orchestrate tool chains | Async tasks + adapters |
| Tool Adapters | Unified adapters | Execute tool, normalize output | Python async + timeouts |
| Orchestrator | DAG / Event Runner | Sequence and retry | Internal scheduler (future Prefect) |
| Validation Layer | Cross Matrix Engine | Compute compatibility matrix | Lightweight Numpy/Scipy |
| Peer Review | Multi-agent evaluators | Scoring and iterative feedback | LLM + heuristic rules |
| Knowledge Layer | Graph + Vector Store | Relational queries + embeddings | SQLite + FTS / FAISS |
| Persistence | DB + MLflow + DVC | States, artifacts, versioning | SQLAlchemy, MLflow, DVC CLI |
| Publication | Package Builder | Manifests, markdown, hashing | Jinja2, BLAKE3 |
| Monitoring | Metrics + Tracing | KPIs + performance + risk | Prometheus client, OTEL future |
| Ethics | Risk Gate | Pre-validations sensitive domain | Rules + JSON taxonomy |

<a id="33-state-machine-del-hypothesis-core"></a>
### 3.3 Hypothesis Core State Machine
Minimum states (Phase 1): `DRAFT -> EXPANDED -> VALIDATED -> REFINED -> PUBLISHED -> ARCHIVED`.
Transitions with guards:
- `expand`: requires `domains_involved` detected.
- `validate`: requires outputs from domain agents + risk gate.
- `refine`: activated if `consensus_score < threshold` or conflicts.
- `publish`: requires `reproducibility_score >= min`, `risk_score <= max`.

- `domain.validation.completed {id, domain, metrics}`
- `cross_validation.updated {id, matrix_hash}`
- `publication.package.ready {id, package_id}`

Each payload validated by Pydantic models (`app.schemas.events`).

<a id="36-resource-scheduler-gpu--cpu"></a>
### 3.6 Resource Scheduler (GPU / CPU)
- Priority queue: `PriorityQueue[(priority, task)]`.
- Initial policy: priority = `scientific_value_weight * expected_impact - resource_cost`.
- Avoid starvation through aging (incremental priority increase based on time in queue).

<a id="37-orchestrator-ligero"></a>
### 3.7 Lightweight Orchestrator
- Receives plan of steps (task list) with dependencies.
- Executes with concurrency semaphore per resource type (GPU, CPU intensive, IO).
- Configurable exponential retries per task.

<a id="38-gestión-de-timeouts-y-circuit-breakers"></a>
### 3.8 Timeout and Circuit Breaker Management
Each Tool Adapter wrapped by resilient wrapper:
```
async def resilient_run(adapter, payload):
    with timeout(adapter.timeout):
        try: return await adapter.run(payload)
        except TransientError: retry
        except FatalError: open_circuit(adapter)
```
Simple in-memory circuit breaker (failure counter window).

<a id="4-diseño-de-domain-agents-y-tool-adapters"></a>
## 4. Domain Agents and Tool Adapters Design

<a id="41-principios"></a>
### 4.1 Principles
- Separation: Agent (scientific logic + orchestration) vs Adapter (invocation of specific tool).
- Interchangeable adapters with hierarchical fallback.
- Unified observability (same metrics contract).

<a id="42-interfaz-base-tooladapter"></a>
### 4.2 Base Interface `ToolAdapter`
```
class ToolAdapter(Protocol):
    name: str
    version: str
    timeout: int
    cost_estimate: float
    async def available(self) -> bool: ...
    async def run(self, payload: dict) -> dict: ...
    def describe(self) -> dict: ...
```
Wrapper standardizes output:
```
{
  "status": "ok|error",
  "started_at": ts,
  "ended_at": ts,
  "metrics": {...},
  "artifacts": [{id,type,uri,hash}],
  "data": {...},
  "errors": []
}
```

<a id="43-registro-dinámico"></a>
### 4.3 Dynamic Registry
```
adapter_registry = {}

def register_adapter(domain: str, adapter: ToolAdapter, priority: int):
    adapter_registry.setdefault(domain, []).append((priority, adapter))
    adapter_registry[domain].sort(key=lambda x: x[0])
```
Selection: try in priority order; if `available()==False` or circuit open, move to next.

<a id="44-ejemplo-cadena-proteica-pipeline"></a>
### 4.4 Protein Chain Example (Pipeline)
1. `ProteinDesignAdapter` (ProtGPT2 / future diffusion)
2. `StructurePredictionAdapter` (AlphaFold3 → fallback ESMFold)
3. `DockingAdapter` (Mock DiffDock → real)
4. `StabilityHeuristicsAdapter` (heuristic estimated DDG)

```
class ProteinDomainAgent(DomainAgent):
    async def evaluate(self, hypothesis: Hypothesis):
        design = await run_adapter_seq("protein.design", payload)
        structure = await run_adapter_seq("protein.structure", {seq: design.data.seq})

        stability = await run_adapter_seq("protein.stability", {pdb: structure.artifacts[0].uri})
        return aggregate_metrics([...])
```

<a id="5-algoritmo-de-validación-cruzada"></a>
## 5. Cross-Validation Algorithm

<a id="51-objetivo"></a>
### 5.1 Objective
Quantify multi-domain coherence, detect conflicts and produce a `consensus_score` for refinement/publication decisions.

<a id="52-entradas"></a>
### 5.2 Inputs
- Metrics per domain: `domain_scores = {domain: {evidence_score, plausibility, risk_local, confidence}}`.
- Graph relationships (edge weights of prior support or conflict).
- Hard rules (biosecurity, ethics) → flags.

<a id="53-construcción-matriz-c"></a>
### 5.3 Matrix C Construction
For ordered domains `D = [d1..dn]`:
```
C[i,j] = {
  compatibility: f(domain_scores[di], domain_scores[dj], edges(di,dj)),
  rationale: str,
  updated_at: ts
}
```
Properties:
- `compatibility ∈ [-1,1]` (approximate symmetry: |C[i,j]-C[j,i]| < ε).
- Diagonal reserved for `self_consistency` = function of internal variance of outputs (if applicable).

<a id="54-función-de-compatibilidad-mvp"></a>
### 5.4 Compatibility Function (MVP)
```
compat(di,dj) = w1 * min(confidence_i, confidence_j) * sign(support - conflict) * log(1+evidence_intersection)
                - w2 * risk_overlap
```
Where:
- `support` = sum of edge weights of type `supports` between result nodes of domains.
- `conflict` = sum of edge weights of type `conflicts_with`.
- `risk_overlap` = average of matching risk components.
- `evidence_intersection` = |set(evidence_i) ∩ set(evidence_j)|.

Initial parameters: `w1=0.6`, `w2=0.4`, `ε=0.05`.

<a id="55-score-global"></a>
### 5.5 Global Score
```
domain_aggregate = Σ_d (α_d * evidence_score_d * confidence_d) - β * Σ_d risk_local_d
compat_term = γ * ( Σ_{i<j} max(0, C[i,j].compatibility) - δ * Σ_{i<j} max(0, -C[i,j].compatibility) )
consensus_score = normalize(domain_aggregate + compat_term - hard_penalties)
```
- `α_d` normalized according to declared domain importance (configurable weight).
- `hard_penalties` = ∞ if hard rule violated → force invalidation.

<a id="56-actualización-incremental"></a>
### 5.6 Incremental Update
When validation of a new domain `dk` completes:
1. Compute rows/columns `C[k,*]` using existing data.
2. Recalculate only `compat_term` incrementally.
3. Update `metrics_snapshot.consensus`.

<a id="57-detección-de-conflictos-críticos"></a>
### 5.7 Critical Conflict Detection
Conditions:
- If ∃ pair (i,j) with `compatibility < -0.7` and both `confidence > 0.6` → mark `conflict_cluster`.
- Trigger event `hypothesis.refine.requested`.

<a id="58-refinamiento-automático-hook"></a>
### 5.8 Automatic Refinement (Hook)
Strategies:
- Request additional evidence (literature adapter) focused on conflicting variables.
- Adjust weights `α_d` reducing impact of domains with high variance.

<a id="59-serialización"></a>
### 5.9 Serialization
Save in `cross_validation_matrix` as:
```
{
  "domains": ["protein","genomics",...],
  "matrix": [[{compatibility:0.9,...}, ...], ...],
  "params": {w1:0.6,w2:0.4,γ:0.5,δ:0.7,β:0.3},
  "version": "cv_matrix.v1"
}
```
Independent hash for structural changes.

<a id="510-testing"></a>
### 5.10 Testing
- Approximate symmetry test.
- Conflict penalty test (negative compatibility reduces global score).
- Edge case: single domain → compat_term = 0.

<a id="511-futuras-extensiones"></a>
### 5.11 Future Extensions
- Bayesian coherence inference (probabilistic graph).
- Weight adjustment by learning (optimization over history of successful hypotheses).

### 6.8 Evidence and Dynamic Weight
Edge weight `supports` updated with formula:
```
new_weight = decay(old_weight, half_life_days) + k * confidence_result

Allows attenuating obsolete evidence.

Periodic validator:

- Need for complex probabilistic traversals.

<a id="612-pruebas"></a>

<a id="8-módulo-de-ética-y-riesgo"></a>
## 8. Ethics and Risk Module

<a id="81-objetivo"></a>
### 8.1 Objective
Prevent execution and publication of hypotheses with high bio/ethical risk without controls; provide transparency and traceability.

<a id="82-taxonomía-inicial-de-riesgos"></a>
### 8.2 Initial Risk Taxonomy
| Category | Examples | Action |
|-----------|----------|--------|
| Biosafety | Pathogens, antimicrobial resistance | Block or human review |
| Chemical | Dangerous synthesis | Flag and reduce priority |
| Dual Use | Weaponization potential | Ethical escalation |
| Sensitive Data | PHI, identifiable genomics | Mandatory anonymization |
| Environmental Impact | High compute emissions | Resource adjustment recommendation |

<a id="83-scoring"></a>
### 8.3 Scoring
```
risk_score = Σ (category_weight * likelihood * impact)
```
Normalized 0-1. Thresholds:
- `>=0.7` → block.
- `0.5-0.7` → require refine / manual gating.

<a id="84-pipeline-de-evaluación"></a>
### 8.4 Evaluation Pipeline
1. Semantic classification (LLM + control lists) on `title/description`.
2. Regex/heuristic rules (e.g. known pathogen sequence hash).
3. Estimated energy consumption calculation (GPU hours * CO2 factor) → `environmental_subscore`.
4. Aggregation + decision.

<a id="85-registro-en-safety_assessment"></a>
### 8.5 Log in `safety_assessment`
```
{
  risk_score: 0.42,
  categories: [{name:"Bioseguridad", score:0.1}, ...],
  decisions: [{gate:"execution", allow:true, rationale:"below threshold"}],
  updated_at: ts
}
```

<a id="86-reglas-duras-fail-fast"></a>
### 8.6 Hard Rules (Fail Fast)
- Sequence matching in blacklist.
- Explicit request for pathogenic synthesis.
- Attempt to deanonymize dataset.

<a id="87-auditoría"></a>
### 8.7 Audit
Each block generates `risk.gate.triggered` event + entry in `validation_history`.

<a id="88-testing"></a>
### 8.8 Testing
- Case: innocuous title → low risk.
- Case: prohibited term → immediate block.
- Case: high energy → elevated environmental subscore.
